## Reading the map

- **PASS boundary** means the named fixture asserts and passes the stated boundary. It does not certify every input or live configuration.
- **EXECUTED TODO defect** means the desired assertion ran and failed against the reviewed implementation. It is an offline reproduction, not evidence of an affected live customer.
- **POLICY TODO** means an executable proposed outcome awaits an owner decision. Passing or failing it does not choose that policy.
- **PARTIAL / scope control** identifies missing end-to-end proof. In particular, a pure renderer or a roster-only reader is not an operational delivery or payment-reconciliation test.

## I15 oracle attribution and limits

The existing mission tests call the real mission route through [test/mission/_harness.mjs](../../test/mission/_harness.mjs). Its independent oracle runs after answered main-route requests (lines 675-676 and 693-708), filters synthetic Stripe data to configured price IDs, and compares entitled customer IDs with roster customer IDs for `paid_not_served` (lines 1216-1219). The converse `served_not_paid` check is conditional on complete Stripe data (lines 1226-1229).

The MC 300-item pagination case includes entitled subscriptions absent from the one-row roster, so the oracle comparison is exercised with a nonzero membership gap. MS price-scope controls exclude the other product. MC `COR-2 revenue: an unreadable subscription list never shows a $0.00 run rate` and MS unavailable/partial cases assert visible uncertainty. These are existing executable oracles, not a new reconciliation implementation.

This is a customer-ID membership check over the configured price set, not proof of subscription-level entitlement, active-row correctness, or actual delivery to every subscription. The new C scope-control test makes no Stripe calls and must not be cited as reconciliation coverage. Runtime configuration, complete live pagination and monitoring cadence remain unverified.
