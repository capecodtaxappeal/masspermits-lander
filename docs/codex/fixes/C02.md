## Reproductions and preserved behavior

The two original I04/C02 roster get/put TODOs are promoted to hard assertions. They now require status 500, `ok: false`, zero customer provider requests, unchanged persisted membership, and no first-delivery log write.

Eleven new hard tests cover:

- Four roster inputs: malformed JSON, object-shaped JSON, JSON null, and a JSON string. Each must return 500, leave the bytes untouched, and make zero customer requests and zero roster writes.
- A roster object whose body read throws. It must stop before customer mail.
- Failed persistence followed by the same event for both new enrollment and reactivation. The failed attempt leaves the previous roster intact and sends nothing; the retry persists the row, preserves an existing token where applicable, and makes one customer provider request with the saved token link.
- Intentional first enrollment when the roster object is absent. It still creates the roster and sends the bundle.
- A delayed roster write. While the write is pending, the roster remains empty and no customer request occurs; after it completes, the handler proceeds. The test always finishes the pending request before restoring the closed transport, including assertion-failure cleanup.

## C02 remains partially open

The two delivery-log TODOs remain unchanged and failing:

- `I04 C02 delivery-log get failure cannot claim complete recoverable delivery`
- `I04 C02 delivery-log put failure cannot claim complete recoverable delivery`

The catch after provider acceptance at source line 217 is intentionally unchanged. Turning it into 500 would request a replay after a potentially accepted customer email without C03 idempotency. Durable first-delivery evidence, an explicit accepted-but-incomplete result, event deduplication, and ambiguous provider acceptance require a coordinated later design. This patch closes only the reproduced pre-provider enrollment failure paths.

Other limits remain:

- A missing roster is still treated as intentional first creation. This patch cannot distinguish that case from accidental deletion.
- The new schema check validates the top-level array only. It does not introduce a complete row schema, repair legacy records, require optional fields, or reinterpret absent `active`.
- Referral-code storage can occur before enrollment. Zero customer requests on failure does not mean zero R2 effects of every kind.
- Whole-roster concurrency and event ordering remain C05/C04b work. Successful put completion does not make the overall multi-event process atomic.
- A storage outage now delays the customer's first bundle until a retry succeeds. That is the intended tradeoff for withholding mail when enrollment could not be established. The retry fixtures inject failed puts before persistence; they do not certify all distributed or ambiguous-commit failure modes.

For D-8 review, retain the ordering of bundle preflight, mandatory enrollment, and customer provider call; preserve the existing post-provider catch; and review the disclosed structural blocker before merge. No sender/status/workflow freeze is lifted.
