## Implementation

`updateSubscriberRoster` at webhook lines 292-315 reads the JSON body and etag from one `get`, validates the top-level array and requires a usable etag for an existing object. It applies the caller's mutation to that snapshot. An unchanged result needs no write.

The sole remaining roster `put` is at lines 304-306. Existing objects use `onlyIf.etagMatches`; first enrollment uses `onlyIf.etagDoesNotMatch: "*"`. A null conditional result means conflict: discard the stale list, reread and rerun the mutation. Each update has four attempts. Read, parse, schema, version and write failures, or exhausted conflicts, throw a static error. The outer webhook catch answers HTTP 500 without storage exception text. No unconditional fallback exists.

Enrollment alone can create an absent object. Missing-roster deactivation, flag and clear calls keep their existing storage no-op behavior and existing caller notification policy. Optional row fields, nested unrelated fields, existing tokens and D2 missing-active eligibility are preserved. The patch does not introduce a full row schema or repair legacy data.

All helper calls precede the relevant provider calls: deletion awaits deactivation at line 43; payment failure awaits marking before owner mail at lines 62-68; Radar awaits deactivation and marking at lines 116-120; review approval awaits clearing before owner mail at lines 145-146; renewal clears at lines 158-161 before customer mail; checkout enrolls at lines 200-206. ## Remaining risks and limits

- A busy roster can exceed four conflicts and delay the webhook until another delivery attempt. The fixture shows recovery when invoked again; live Stripe retry configuration and eventual processing were not checked.
- A put may commit and then lose its acknowledgement. No provider request from that invocation has occurred yet; the new failure path does not follow provider acceptance within that invocation. This does not establish event idempotency: subsequent event handling retains the existing C03 duplicate/ambiguous-provider limits.
- Conditional writes prevent lost updates among the participating writers. They do not impose event-time order, protect against an outside unconditional writer, or make the roster and provider one transaction.
- Radar uses two separate roster updates. The first may persist before the second fails; there is no rollback. Retry completes the remaining bookkeeping before owner mail, and per-attempt counts can differ. This patch does not redesign the owner wording or hold policy.
- Missing storage is intentionally different from unreadable storage: only enrollment creates an absent roster. This cannot distinguish intentional first creation from accidental object deletion.
- Top-level-array validation does not certify every row. Existing matchers and D2 behavior are retained rather than silently normalized.
- Provider capture/acceptance is not inbox receipt. No service, credential, real dataset, workflow execution, forced resend, billing change or customer contact was used.
